# Gap Demos, Objections, and Price

Use this reference for demos, product presentations, objection handling, price resistance, budget pushback, or buyer contradictions.

Source refs: *Gap Selling*, Ch. 11 and Ch. 13; see [`sources.md`](sources.md).

## Demo Framework

There are four demo rules.

### 1. No discovery, no demo

A demo is valid only after discovery answers:

1. Does the prospect have a problem you can fix?
2. Does the prospect agree they have it?
3. Does the prospect want to fix it?
4. Will the prospect go on a journey with you to fix it?

If discovery is missing, refuse or reschedule the demo as a two-step process: discovery first, demo later.

Completion bar: never create a demo flow until the buyer's current state, future state, and problems are known.

### 2. No “if”

Do not say “if you have this problem.” In a gap demo, you should already know the problem.

Bad:

> “If your team struggles with reporting, this feature helps.”

Good:

> “You said monthly reporting takes 12 hours and delays board updates. This workflow reduces the manual steps causing that delay.”

Completion bar: every feature is tied to a discovered problem, not a hypothetical.

### 3. Stick to six features

Show only the features needed to solve the buyer's serious business problems. More features create distraction and lower perceived relevance.

Completion bar: each feature maps to a problem, impact, root cause, or future-state outcome.

### 4. Anchor the buyer

After each feature, ask an affirming question that ties the feature to the future state:

- “Can you see how this would improve [business outcome]?”
- “Do you see how this would reduce [current-state impact]?”
- “Would this help you get to [future state]?”

If the buyer says no, stop the demo and return to discovery.

Completion bar: the buyer verbally connects the solution to their desired outcome.

## Demo Map

Use the PIC as the demo map:

```text
Problem -> Impact -> Root cause -> Feature/approach -> Future-state effect -> Affirming question
```

Example structure:

| Problem | Impact | Root cause | Show | Anchor question |
|---|---|---|---|---|
| [buyer problem] | [business cost] | [cause] | [feature/process] | “Can you see how this gets you to [outcome]?” |

## Objection Framework

Do not defend the product. Compare the objection to the buyer's desired future state.

Ask:

- Does solving this objection move them closer to their desired outcome?
- Is this a real business issue or a preference?
- Did we misunderstand their current state?
- Did a new stakeholder introduce a different current state?

If the objection matters, solve it or qualify out. If it conflicts with their stated priorities, use the confusion pattern.

## “I'm Confused. You Said…” Pattern

Use when buyer words and buyer actions conflict.

Structure:

```text
I'm confused. You said [problem/future state/intrinsic motivation].
But now [objection/action] seems to move away from that.
Did I misunderstand [their priority], or has something changed?
```

This works because it lets the buyer save face: the possible misunderstanding is yours, so they can explain without feeling attacked.

Completion bar: the buyer must either defend the objection, correct the seller's understanding, or realign to the original outcome.

## Price Objections

Three common forms:

1. “It's too expensive.”
2. “We don't have the budget.”
3. “We can't afford it.”

### “It's too expensive”

Return to the value of the gap.

Template:

> “I'm confused. You said [solution] would help you achieve [future-state value] and avoid [current-state cost]. How is [price] too expensive compared with [gap value]?”

Then stop talking. Let the buyer explain.

### “We don't have the budget”

A budget objection means money may exist but was not allocated. Compare delay to cost of inaction.

Template:

> “I understand. I'm confused, though: if you wait until the next budget cycle, you said [problem] will continue costing [impact]. Are you prepared to absorb that cost for [time period]?”

### “We can't afford it”

Affordability means the buyer may genuinely lack access to money. If true, qualify out or restructure only if it still protects value.

Ask:

- “Is this a budget allocation issue or an affordability issue?”
- “If the value case were clear, is there a way to fund it?”
- “What would need to be true for this to be financially possible?”

Completion bar: do not discount until you know whether the issue is value, budget allocation, or actual affordability.

## Trial or Unreasonable Demand Framework

If a buyer asks for a trial, custom work, pricing, or concessions without giving information or commitment, do not become the customer's servant.

Options:

1. Say no if it prevents good selling or creates one-sided risk.
2. Set terms that make risk mutual.

Trial terms example:

- Buyer pays an installation/onboarding fee.
- Buyer provides success criteria.
- Buyer commits to purchase if success criteria are met.

Completion bar: seller concessions require buyer commitments of equal or greater value.
