# ADDIE — End-to-End Practitioner Checklist

> Source: Pastore, R. (2020). *The Instructional Design and Development Process: A 'How To' Guide for Practitioners*. KDP. ISBN 9798651489978.

A linear checklist to run a full ADDIE project. Print this. Tick the boxes.

## Phase 1 — Analysis

### Front-End Analysis (FEA)

- [ ] Training Charter started day 1 (client, problem, cause, intervention, stakeholders, managers, SMEs, ROI, budget, schedule) — pp. 26–27
- [ ] Initial meeting(s) with client + manager + SME held (or one phone call max) — p. 18
- [ ] Information gathered: interviews, observations, surveys, document analysis — p. 18
- [ ] "Why" exercise run to find root cause — p. 18
- [ ] Confirmed: training is actually the right intervention (NOT communication / system / motivation) — p. 15
- [ ] Gap Analysis table built (Current / Desired / Recommended Solution) — p. 20
- [ ] Multiple solution options presented (not just "dream desired state") with ROI/budget/timeline — pp. 19–20

### Needs Analysis

- [ ] Learner Analysis: education, computer literacy, age, motivations, work conditions, preferences — p. 29
- [ ] Context Analysis: environment, technology, LMS, tech budget — pp. 30–31
- [ ] LMS pinned down by name (not "we have one somewhere") — p. 31
- [ ] Content walkthrough with SME completed; realistic content volume estimate — pp. 33–34
- [ ] Project goals (PM-style) written — p. 34
- [ ] Instructional goals (general) written — p. 34
- [ ] Proposal / SOW with budget + schedule signed off by client — p. 35

### Task Analysis

- [ ] High-level tasks broken from goals — p. 36
- [ ] Each task scored 1–10 on importance, difficulty, length, cost — p. 38
- [ ] Tasks decomposed until prior knowledge takes over — pp. 37–39
- [ ] Format chosen: list (1.0 / 1.1 / 1.1.1) or tree (Figure 3.0) — pp. 41–42
- [ ] **SME/client signed off on task analysis** — p. 36
- [ ] Templates started during task analysis — p. 36

### Analysis Document

- [ ] Training charter summary
- [ ] FEA results
- [ ] Learner + Context analysis results
- [ ] Project solution + goals
- [ ] High-level prioritized task list
- [ ] Full task analysis
- [ ] Document signed off by client — pp. 43–44

## Phase 2 — Design

### Learning Objectives

- [ ] One ABCD objective per task — pp. 45–50
- [ ] Audience defined (or implied)
- [ ] Behavior is an observable action verb (NOT "understand"/"remember") — p. 48
- [ ] Condition specified
- [ ] Degree specified (or implied 100%)
- [ ] One verb per objective; one objective per sentence — p. 49
- [ ] Objective level matches task complexity (low/high knowledge) — p. 47

### Instructional Congruency

- [ ] Three-column table built: Task / Objective / Assessment — Table 5.0, pp. 51–52
- [ ] Every objective has an assessment item
- [ ] Every assessment item ties back to an objective
- [ ] Every objective ties back to a task

### Assessments

- [ ] Pretest written — p. 55 (mandatory)
- [ ] Posttest written, aligned to pretest
- [ ] Question types match knowledge level (Table 6.0, p. 56)
- [ ] Question quality checks done (no "always/never", no answer patterns, plausible distractors, NOT highlighted) — p. 57
- [ ] If performance assessment: rubric written
- [ ] Rubric has objective per-box descriptors (NOT "Great/OK/Poor") — p. 61
- [ ] Rubric weights reflect actual importance — p. 61

### Strategies

- [ ] Organizational strategy chosen (e.g., Gagné's 9 Events) — p. 64
- [ ] Delivery strategies chosen per phase (Keller ARCS, PBL, games, etc.) — pp. 69–70
- [ ] Strategy mapping documented (Pastore phase ↔ Gagné event ↔ delivery method)

## Phase 3 — Development

### Pre-build

- [ ] Storyboards built (paper prototype first if possible) — pp. 76–80
- [ ] Storyboards signed off by client (quality checkpoint) — p. 77
- [ ] Style guide created: fonts, colors, resolution, buttons, spacing, formatting, SCORM, code comments — pp. 81–83

### Build

- [ ] Authoring tool chosen (Articulate / Captivate / PowerPoint / Lectora) — p. 85
- [ ] Mayer's multimedia principles applied (multimedia, split attention, modality, redundancy, coherence, contiguity, signaling, interactivity) — p. 93
- [ ] Usability guidelines applied (consistent, minimal cognitive load, feedback, marked exits, help docs) — pp. 95–96
- [ ] Pro voice talent for narration (no full text-to-speech) — pp. 73–74

### Pilot Testing

- [ ] **Alpha test** on client's actual hardware/LMS — p. 97
- [ ] **Beta test** with real users in small groups; observe — pp. 97–98

## Phase 4 — Implementation

- [ ] Lessons-learned document started — p. 99
- [ ] LMS configured and tested
- [ ] Train-the-Trainer plan finalized (which TTT model applies?) — p. 100
- [ ] Change management touchpoints scheduled — p. 100
- [ ] Communication plan sent to stakeholders — p. 100
- [ ] Baseline performance data captured (for L4) — p. 100
- [ ] Pretest data captured (for L2) — p. 100
- [ ] Owner identified for post-handoff maintenance

## Phase 5 — Evaluation

### Plan upfront

- [ ] L1 satisfaction instrument designed
- [ ] L2 pretest + posttest finalized
- [ ] L3 transfer measurement plan: what, who, when, how — p. 104
- [ ] **L4 ROI metric agreed in writing with client** — pp. 104–105
- [ ] Reporting cadence agreed (when does client see L1? L3? L4?)

### Execute

- [ ] L1 collected at end of course
- [ ] L2 calculated: posttest – pretest = learning gain
- [ ] L3 collected weeks/months later — p. 104
- [ ] L4 calculated against pre-defined metric

### Report (p. 105)

- [ ] Background / Client
- [ ] Stakeholders
- [ ] Key Questions
- [ ] Model selected (Kirkpatrick)
- [ ] Data Collection and Findings
- [ ] Recommendations

## Top 10 ways this project will fail (Pastore's warnings)

1. Trusted client's stated problem without verifying — pp. 15, 108
2. Recommended a model before hearing the problem — p. 23
3. Skipped content walkthrough; budget blew up — pp. 33–34
4. Used "understand" or "remember" as action verb — p. 48
5. No pretest → can't prove learning — pp. 55–56
6. Bad rubric (subjective titles, equal weights) — p. 61
7. Didn't get storyboard sign-off — p. 77
8. Skipped style guide because solo — pp. 82–83
9. Treated L1 satisfaction as L2 learning — p. 104
10. Didn't define L4 ROI metric upfront — pp. 104–105
