# Implementation — Roll It Out

> Source: Pastore, R. (2020). *The Instructional Design and Development Process: A 'How To' Guide for Practitioners*. KDP. ISBN 9798651489978.

The shortest section in Pastore's book (pp. 99–101) but high-leverage. Bad implementation kills good content.

> "A poor implementation can make the greatest training seem terrible." — Pastore 2020, p. 101

## ADDIE is not strictly linear

> "Implementation takes place throughout the entire process. So even though I have it as a section here, it doesn't mean it has to wait until the end. Remember, the ADDIE process isn't linear." (p. 99)

Implementation activities (LMS setup, communication plan, change-management touchpoints) start as soon as you have something to deploy — not after evaluation.

## What happens here

| Activity | Notes |
|---|---|
| Lessons-learned document | Created during implementation; captures what to do differently next time |
| LMS setup / course shell | Install the software; configure the course in the LMS |
| Train the trainer (TTT) | Train trainers, SMEs, or be the trainer yourself |
| Change management | Walk client through the organizational change |
| Communication | Stakeholders aware of training + impacts + timing |
| Data collection | Gather baseline + during-implementation data needed for L3/L4 evaluation |

## Train the Trainer (TTT) — what it means

(p. 100)

Multiple meanings depending on context:

- Training a **trainer-of-trainers** (cascading model)
- Training **many trainers** at once
- Training the **SMEs** to become trainers
- **Being the trainer yourself**

Identify which one applies in your engagement before you design the TTT material.

## Change management

(p. 100)

> "Change models are beyond the scope of this text."

Pastore name-checks **ADKAR** (Awareness, Desire, Knowledge, Ability, Reinforcement) as one example but doesn't go deeper. The ID's job is to know enough about change processes to walk the client through them — not to be a full change consultant.

If you need more depth, look up:
- ADKAR (Prosci)
- Kotter's 8 Steps
- Lewin's 3-stage model

## Communication plan

(p. 100)

Before launch, stakeholders need to know:
- What training is rolling out
- Who it affects
- When it happens
- What's expected of them
- How they'll know it worked

## Data collection — look ahead to evaluation

(p. 100)

Don't wait until after launch to start collecting data for evaluation. By then, baselines are gone.

Collect during implementation:
- Baseline performance metrics (for L4 ROI later)
- Pretest scores (for L2 learning gain)
- Initial L1 satisfaction touchpoints

## Where IDs hand off

(p. 99)

> "Many times this is where my job as an ID stops."

Common reality: the ID's contract ends with handoff. Make sure:
- Lessons-learned doc is delivered
- TTT is complete
- Owner is identified for the deployed product
- Evaluation plan is in motion

## Common mistakes

| Mistake | Page | Consequence |
|---|---|---|
| Treating implementation as final phase only | 99 | LMS breaks at launch; nothing's tested |
| Skipping change management | 100 | Learners resent the rollout; adoption stalls |
| No communication plan | 100 | Stakeholders surprised; training feels imposed |
| Not collecting baseline data | 100 | Can't measure L3/L4 later |
| Hand-off without lessons-learned doc | 99 | Same mistakes recur next project |
| Assuming the trainer can wing it | 100 | Trainer mis-delivers; great content fails |

## Implementation checklist

- [ ] LMS configured and tested on production stack (not your dev box)
- [ ] Course launched in pilot section before full rollout
- [ ] Trainer trained (or you're the trainer and have notes)
- [ ] Stakeholder communication sent (timing, expectations, FAQ)
- [ ] Change management touchpoints scheduled
- [ ] Baseline performance data captured for L4
- [ ] Pretest data captured for L2
- [ ] Lessons-learned doc started
- [ ] Owner identified for post-handoff maintenance
- [ ] Evaluation plan ratified by client
